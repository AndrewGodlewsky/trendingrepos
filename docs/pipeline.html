Architecture

The pipeline is a daily Python script that runs locally on Windows, stores everything in a SQLite database, and publishes a pre-rendered static HTML site to Cloudflare Pages via GitHub. No server is required to view the site.

What runs where
  • Pipeline — runs locally on your Windows machine via Task Scheduler at 8:00 AM daily
  • Database — data/trending.db lives on your machine only, never pushed to GitHub
  • Website — docs/index.html is pushed to GitHub; Cloudflare Pages serves it
  • Secrets — .env file, never committed
Key numbers
  • 200 repos fetched and ranked per daily run
  • 116k+ repos matching the search query on a typical day
  • 1,532,995 rows in the DB (16 days of history seeded)
  • ~66 seconds average pipeline runtime (warm cache)
  • ~23 minutes first run (all 200 repos need Claude summaries)
  • ~$0.002 Claude Haiku cost per new repo summary

End-to-End Data Flow

Step 1  Fetch

fetcher.py::fetch_and_rank(cfg) is called by run_pipeline.py.

  1. storage.rotate_snapshots() is called — this is now a no-op (SQLite retains history natively).
  2. github_client.fetch_trending(pat, min_stars, days_back) is called as a generator, yielding batches of raw API item dicts.
  3. Each dict is converted to a RawRepo dataclass via RawRepo.from_api_dict().
  4. ranker.rank_repos(raw_repos, top_n) deduplicates, scores, sorts, and caps to 200.
  5. storage.load_previous_repos() reads the second-most-recent run from the DB.
  6. storage.compute_star_deltas(current, previous) computes per-repo star differences and attaches them as stars_7d on each RankedRepo.
  7. storage.save_repos(data_dir, ranked_dicts) inserts into daily_snapshots for today's date.
Step 2  Summarise

summarizer.py::summarize_all(cfg) is called next.

  1. storage.load_repos(data_dir) loads today's 200 repos from DB.
  2. storage.load_summaries(data_dir) loads all existing summaries (keyed by html_url).
  3. For each repo whose html_url is not in the summaries dict (or has an ERROR: prefix), a new summary is generated.
  4. collect_repo_context(owner, repo, token) fetches from GitHub: README (≤8000 chars), file tree (top 200 paths), key config files, entry-point source. Total context capped at 20,000 chars.
  5. Context is sent to Claude with a prompt requesting a 2–4 sentence summary and 1–5 tags. Response is JSON-parsed.
  6. After each successful summary, storage.save_summaries() upserts immediately — partial progress is never lost on crash.
Step 3  Generate Site

site_generator.py::generate(cfg) is called last.

  1. storage.load_repos(data_dir) loads today's ranked repos.
  2. storage.load_summaries(data_dir) loads all summaries.
  3. _enrich_repos() merges summary + tags onto each repo dict.
  4. For each repo, storage.get_history(data_dir, github_id, days=31) is called to retrieve up to 31 days of daily star counts. From this, stars_24h, stars_7d, and stars_30d deltas are computed by finding the closest snapshot ±2 days ago for each window.
  5. _collect_unique_languages() and _collect_top_tags() build the filter metadata.
  6. _render_html() generates the full index.html string — all CSS and JS inlined.
  7. Result is written atomically to docs/index.html.

GitHub API — github_client.py

Search query

GET https://api.github.com/search/repositories
    ?q=pushed:>=YYYY-MM-DD stars:>=50
    &sort=stars
    &order=desc
    &per_page=30
    &page=N

Headers:
    Accept: application/vnd.github+json
    X-GitHub-Api-Version: 2022-11-28
    Authorization: Bearer <GITHUB_PAT>

The pushed date is computed as today - FETCH_DAYS_BACK days. stars threshold is FETCH_MIN_STARS.

GitHub Search API cap: The Search API returns a maximum of 1,000 results per query regardless of how many repos match. On a typical day 116k+ repos match; only the top 1,000 by star count are accessible. The pipeline fetches all 1,000 and lets the ranker pick the top 200 by trending score — so the final 200 are not just the most-starred, they are the most-trending within the top 1,000 most-starred.

Fetcher — fetcher.py

Public API: fetch_and_rank(cfg: dict) → list[dict]

Execution steps

  1. storage.rotate_snapshots(data_dir) — no-op with SQLite backend (returns False), kept for compatibility.
  2. Calls github_client.fetch_trending() as a generator, accumulating all raw item dicts.
  3. Converts each valid item to RawRepo via RawRepo.from_api_dict(). Malformed items are logged and skipped.
  4. Calls ranker.rank_repos(raw_repos, top_n) → returns sorted list[RankedRepo].
  5. Loads previous snapshot via storage.load_previous_repos(data_dir) (the second-most-recent run_date in the DB).
  6. Calls storage.compute_star_deltas(current_dicts, previous) → dict[github_id → delta | None].
  7. Attaches delta to each RankedRepo.stars_7d field (note: name is legacy — this is actually a 1-run delta, i.e. roughly 24h).
  8. Calls storage.save_repos(data_dir, final_dicts) — inserts all 200 rows for today.
stars_7d naming note: The stars_7d field on the DB row and dataclass is a 1-day delta (today vs. the previous pipeline run). The name is a legacy artefact. Actual 7-day and 30-day deltas are computed fresh in site_generator.py using storage.get_history().

Ranker & Scoring — ranker.py

Public API: score(repo: RawRepo) → float and rank_repos(raw_list, top_n) → list[RankedRepo]

Composite score formula

score = star_velocity  × 0.50
      + fork_ratio     × 0.15
      + watcher_ratio  × 0.10
      + recency_bonus  × 0.20
      + issue_health   × 0.05
SignalWeightFormulaRangeIntent
star_velocity 50% stars / max(1, min(365, repo_age_days)) 0 → ∞ (uncapped) Stars per day of existence. Dominant signal. A 6-month-old repo with 18k stars scores higher than a 10-year-old repo with 50k stars.
fork_ratio 15% forks / max(1, stars) 0 → ~1 (rarely >1) People building on the code. A repo where 30% of stargazers also fork it is likely a tool/library people actively use.
watcher_ratio 10% watchers / max(1, stars) 0 → 1 (usually ~1.0) Watchers opt-in to notifications, indicating deeper engagement than passive stars.
recency_bonus 20% max(0, 1 - days_since_push / 30) 0 → 1.0 Linear decay over 30 days since last push. Full bonus if pushed today; zero bonus if not pushed in 30+ days. Penalises abandoned repos.
issue_health 5% 1 / (1 + (open_issues / max(1, stars)) × 10) 0 → 1.0 Penalises repos drowning in issues. A repo with open_issues = 10% of stars scores ~0.5; one with open_issues = 1% of stars scores ~0.91.

rank_repos() pipeline

  1. Deduplicate by github_id — keep the entry with the higher star count if duplicates exist across API pages.
  2. Score each unique repo via score().
  3. Sort descending by score.
  4. Slice to top TOP_N_REPOS (default 200).
  5. Assign ranks 1 through N.
Important: score() uses date.today() for computing repo age and recency. Historical imports use a patched version that uses the snapshot date instead — ensuring historical scores are accurate for that point in time.

Caching logic

A repo is skipped if its html_url already exists in the summaries table and the summary does not start with "ERROR:". Error-prefixed summaries are retried on the next run. This means on most daily runs only 0–5 new summaries are generated.

Incremental saves

storage.save_summaries() is called after every single repo — not at the end. If the pipeline crashes or is interrupted mid-run, all summaries up to that point are preserved in the DB.

Multi-period delta computation

For each repo, storage.get_history(data_dir, github_id, days=31) returns up to 31 rows of {run_date, stars, rank, trending_score} ordered oldest-first. Deltas are then computed:

stars_by_date = {row["run_date"]: row["stars"] for row in history}

def delta_n_days(n):
    for offset in range(n, n + 3):  # ±2 day tolerance
        d = (date.today() - timedelta(days=offset)).isoformat()
        if d in stars_by_date:
            return current_stars - stars_by_date[d]
    return None  # no data for this window

stars_24h = delta_n_days(1)   # vs ~1 day ago
stars_7d  = delta_n_days(7)   # vs ~7 days ago
stars_30d = delta_n_days(30)  # vs ~30 days ago

If no snapshot exists for a given window (e.g. the repo is new to the list), the value is None and the card shows no badge for that period.

Tag cloud generation

_collect_top_tags(repos, limit=60) counts both AI-generated tags and GitHub topics across all 200 repos. Returns up to 60 (tag, count) tuples sorted by frequency. These are rendered as clickable pills in the tag cloud section.

Historical Import — import_historical.py

One-time script to load CSV snapshots from previous pipeline runs into the SQLite DB.

CSV format expected

snapshot_date,github_id,full_name,name,description,stars,forks,watchers,
open_issues,language,topics,license,homepage,html_url,created_at,updated_at,pushed_at

# topics is pipe-separated: "python|cli|tool"
# snapshot_date is YYYY-MM-DD (read from the column, not the filename)

Import process per file

  1. Read all rows into memory (40MB file ≈ 117k rows).
  2. Determine run_date from the snapshot_date column of the first row.
  3. Skip the file if that date already has rows in the DB.
  4. Compute trending score for each row using snapshot_date as "today" (so historical scores reflect the correct point in time).
  5. Sort rows by score descending, assign ranks 1–N.
  6. Bulk-insert in batches of 2,000 using INSERT OR IGNORE (skips duplicate (run_date, github_id) pairs).

Post-import back-fill

After all CSV files are loaded, a single SQL UPDATE computes stars_7d for every null row by comparing to the nearest prior run:

UPDATE daily_snapshots
SET stars_7d = stars - (
    SELECT prev.stars FROM daily_snapshots prev
    WHERE prev.github_id = daily_snapshots.github_id
      AND prev.run_date < daily_snapshots.run_date
    ORDER BY prev.run_date DESC LIMIT 1
)
WHERE stars_7d IS NULL AND (<prior snapshot exists>);

Re-running safely

The script is idempotent. Run it again with new CSV files — existing dates are skipped entirely, new dates are inserted. Use --dry-run flag to preview without writing.

Filter Logic & Thresholds

All filtering happens client-side in JavaScript embedded in docs/index.html. No server is involved.

Period filter — periodOk(card)

The period filter uses a percentage of total stars as its threshold:

function periodOk(card) {
  if (period === 'all') return true;

  var gained;     // stars gained in the window
  var threshold;  // minimum fraction of total stars required

  if      (period === '24h') { gained = card.dataset.stars24h; threshold = 0.30; }
  else if (period === '7d')  { gained = card.dataset.stars7d;  threshold = 0.60; }
  else if (period === '30d') { gained = card.dataset.stars30d; threshold = 1.20; }

  if (gained === '' || gained == null) return true; // no data → show repo

  var total = parseInt(card.dataset.stars, 10);
  if (total === 0) return true;

  return (parseInt(gained, 10) / total) >= threshold;
}
PeriodThresholdMeaningExample: 10k star repo
24h ≥ 30% Gained ≥ 30% of total stars in a single day — genuine viral spike Must gain ≥ 3,000 stars yesterday
7d ≥ 60% Gained ≥ 60% of total stars over the past week — sustained rapid growth Must gain ≥ 6,000 stars in 7 days
30d ≥ 120% Gained more stars in one month than its entire prior history — explosive breakout Must gain ≥ 12,000 stars in 30 days
All — No filter applied; all 200 repos shown —
Missing data behaviour: If a repo has no historical data for a given window (e.g. it's new to the list and we don't have a snapshot from 7 days ago), it is shown rather than hidden. The filter only excludes repos where we have data AND the threshold is not met.

Language filter — langOk

Exact string match: card.dataset.lang === selectedLanguage. Empty selection = all languages. The dropdown is populated from the unique non-null language values in today's 200 repos.

Tag filter — tagsOk(card)

OR logic: a card passes if it has at least one of the selected tags. Tags are stored on each card as a pipe-separated string in data-tags. Both AI-generated tags (from Claude) and GitHub topics are included.

card.dataset.tags = "python|cli|llm|machine-learning|transformer"
// Split on '|' to get the list for comparison

Min Stars filter — starsOk(card)

Compares parseInt(card.dataset.stars) against the dropdown value (0, 1000, 5000, 10000, 50000, 100000).

Search filter — searchOk(card)

Case-insensitive substring match across: repo full_name, description text, AI summary text, and tags (pipe-separated string converted to spaces). Debounced 200ms to avoid filtering on every keystroke.

data-stars7dinteger string or """120"Period filter (7d), delta badge
data-stars24hinteger string or """45"Period filter (24h), delta badge
data-stars30dinteger string or """890"Period filter (30d), delta badge

Empty string ("") means no historical data is available for that window. The JS filters treat empty as "no data → show the repo".

Sort Logic

Sorting is applied after filtering. The DOM is re-ordered by moving card elements with grid.appendChild(), which places visible cards first (sorted by the selected key) and hidden cards at the end.

Sort optionComparatorNotes
Trending (default) parseInt(a.dataset.rank) - parseInt(b.dataset.rank) Lower rank number = higher position. Rank 1 = most trending by composite score.
Most Stars parseInt(b.dataset.stars) - parseInt(a.dataset.stars) Descending by total star count. A classic GitHub popularity sort.
Most Forks parseInt(b.dataset.forks) - parseInt(a.dataset.forks) Descending by fork count. Surfaces repos people are actively building on.

The delta badge in each card footer updates dynamically when the period toggle changes via updateDeltaBadges(period), which reads the appropriate data-stars* attribute and formats it as +N 24h / +N 7d / etc.

Branch protection on master

The master branch has protection rules enabled: force pushes are blocked and the branch cannot be deleted. Normal git push from the pipeline works fine — only destructive operations are prevented.
